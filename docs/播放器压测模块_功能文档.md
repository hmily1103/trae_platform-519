# 播放器压测模块功能文档

## 1. 文档目的

本文档用于说明 `player_stress` 模块当前版本的业务目标、功能范围、用户操作方式、报告含义、适用场景与边界，面向以下角色：

- 测试同学：了解如何配置、执行、查看结果
- 研发同学：了解报告输出了什么、能回答什么问题
- 产品/管理层：快速理解这套工具的价值、限制和结论口径

模块路径：

- `D:\trae-code\trae_platform\modules\player_stress`

Web 入口：

- `http://127.0.0.1:5000/player_stress/`

---

## 2. 模块目标

播放器压测模块的核心目标不是“单纯跑时长”，而是围绕电视端播放体验建立一套可重复、可溯源、可归因的自动化监控体系，重点解决以下问题：

1. 电视端是否真的发生了卡顿、冻结、解码停顿
2. 卡顿更偏播放器/解码侧，还是系统/固件资源竞争侧
3. 风险是否达到了阻断上线的程度
4. 当证据不够时，明确告诉使用者“当前还差什么”

---

## 3. 核心能力概览

### 3.1 测试执行能力

支持以下模式：

- `monitor_only`
  - 纯监控模式
  - 不主动点歌
  - 适合轮播、旁路播放、现场播放观察
- `loop_playback`
  - 循环播放/点歌模式
  - 适合业务链路稳定性验证
- `fixed_skip`
  - 固定间隔切歌
  - 适合切歌场景压力验证

### 3.2 电视端专项监控能力

围绕电视端 `Display 1` / 自动识别 Display 建立多源证据链：

- Display 身份识别
- 视频 Surface 锁定
- 视频 FPS 采集
- 帧间隔异常检测
- 电视端卡顿事件检测
- 电视端冻结事件检测
- 解码停顿检测
- OSD 叠加层辅助观测

### 3.3 资源与稳定性监控能力

持续采集：

- 播放器进程 CPU
- 整机 CPU
- 内存 PSS
- 进程 PID 生命周期
- 重启 / 进程丢失
- Crash / ANR
- 重复高负载进程
- 温度 / CPU 频率（设备支持时）

### 3.4 报告与证据输出能力

输出文件：

- CSV 明细报告
- TXT 摘要报告
- JSON 摘要
- HTML 可视化报告
- 单事件证据目录

支持按事件落盘的证据：

- `event.json`
- `event_summary.txt`
- `top_before.txt`
- `top_after.txt`
- `cpu_during.jsonl`
- `time_window_logcat.txt`
- 截图文件

## 4. 典型使用场景

### 4.1 快速冒烟

目的：

- 看新版本是否一上来就挂
- 看是否出现明显高 CPU、进程重启、明显电视端异常

建议配置：

- `monitor_only`
- 10~30 分钟

适合判断：

- 能不能继续深入测
- 是否存在明显致命问题

### 4.2 上线前稳定性验证

目的：

- 判断版本是否具备放行基础

建议配置：

- `loop_playback` 或真实业务播放
- 至少 60 分钟

适合判断：

- 有无长期 CPU 累积竞争
- 有无热降频迹象
- 有无持续性卡顿趋势

### 4.3 归因定位

目的：

- 某版肉眼看到卡顿，想知道是谁的问题

建议配置：

- 保留实时监控
- 保留事件证据目录

适合判断：

- 是否是播放器单进程问题
- 是否是系统进程 / 固件脚本抢占 CPU
- 是否是解码链路停顿

## 5. 页面功能说明

### 5.1 测试配置页

主要配置项：

- 目标设备
- 测试包名
- 测试模式
- 监控时长
- 切歌检测关键字
- 采样间隔
- Display 配置
- HTTP 点歌配置（可选）

作用：

- 决定测试对象、采样强度和是否主动驱动播放

### 5.2 实时监控页

实时展示：

- 当前状态：未开始 / 运行中 / 已完成 / 异常结束
- 进度条、倒计时、已运行时长
- 机顶盒 IP
- 固件版本
- Display 身份
- 视频 FPS
- CPU 使用率
- 播放歌曲数
- 内存占用
- 解码器状态
- 电视端卡顿状态
- CPU 竞争归因
- 最近电视端异常事件

说明：

- 这是测试过程中的在线诊断面板
- 适合边跑边观察趋势
- 真正用于归档和评审的仍然是最终报告

### 5.3 实时日志页

展示测试执行过程中的日志：

- 设备连接
- 线程启动
- 监控采样
- 异常事件
- 报告生成

作用：

- 辅助定位“为什么这次测试没跑起来”
- 辅助定位“为什么刚开始就异常结束”

### 5.4 历史报告页

展示历史测试结果：

- CSV / TXT / JSON / HTML 文件
- 报告下载
- 历史回看

## 6. 报告核心结论口径

### 6.1 当前准入结论分级

系统当前将准入结论拆为四档：

- `建议上线`
  - 未触发阻断项
  - 风险样本较少或无风险
- `建议灰度观察`
  - 没有确认级阻断问题
  - 但风险样本较多，建议带监控灰度放量
- `证据不足，暂不作上线结论`
  - 证据链不完整
  - 当前报告不适合一锤定音
- `不建议上线`
  - 已出现阻断项
  - 或稳定性明显不达标

### 6.2 风险口径

报告将电视端异常分成三类：

- 确认级卡顿
- 风险样本
- 冻结样本

并进一步区分：

- 冻结确认
- 冻结风险
- 已忽略冻结

这样可以避免“只要截图不动就算卡顿”的误报。

### 6.3 证据可信度

报告会给出证据可信度，用来回答：

- 这次结论到底有多稳
- 是直接证据闭环，还是仅风险提示

影响因素包括：

- Display 是否识别
- Surface 是否锁定
- FPS 是否采集成功
- 是否有确认级卡顿/解码停顿
- 是否仅有风险样本

---

## 7. 报告重点字段说明

### 7.1 首页摘要

回答四个问题：

1. 一句话结论是什么
2. 上线判断是什么
3. 谁先处理
4. 为什么这么判断

### 7.2 稳定性评分

反映：

- Crash / ANR
- PID 重启 / 丢失
- 屏幕异常
- 资源异常

说明：

- 稳定性评分不等同于电视端流畅度评分

### 7.3 电视端卡顿风险分

反映：

- 人眼感知层面的电视端流畅度风险

说明：

- 这是体验观察维度
- 不单独决定是否上线

### 7.4 风险口径

反映：

- 当前是“无风险 / 未闭环风险 / 阻断性问题”

### 7.5 研发处理优先级

直接回答：

- 先查谁
- 看什么日志
- 平台已提供什么证据
- 怎么复测

### 7.6 电视端异常事件明细

按事件粒度展示：

- 时间
- 持续时长
- 事件类型
- 等级
- 研发一句话结论
- 关键依据
- 建议动作
- CPU 嫌疑进程
- 证据目录

### 7.7 OSD 叠加层观测

用于回答：

- 跑马灯 / 二维码 / Logo 等 OSD 是否可能影响最终显示

### 7.8 工具自身开销

用于回答：

- 监控工具自己有没有引入明显干扰

## 8. 当前能力边界

这套工具当前已经能做很多自动判断，但仍然有明确边界：

1. 30 分钟以内更适合初筛，不适合正式长期稳定性结论
2. `monitor_only` 不能替代完整业务负载压测
3. 不同主板平台的证据能力不完全一致
4. 没有 Surface / FPS / decoder 直证时，只能给风险提示，不能强行定责
5. OSD 层识别依赖 Surface 命名和平台能力，不保证每个设备都 100% 识别

---

## 9. 推荐使用规范

### 9.1 用于初筛时

推荐：

- 10~30 分钟
- `monitor_only`
- 快速看崩溃、CPU、风险样本

### 9.2 用于上线评审时

推荐：

- 至少 60 分钟
- 尽量使用真实业务负载
- 结合 HTML 报告与事件证据目录
- 不只看“建议上线”，也要看“风险口径”和“证据可信度”

### 9.3 用于根因定位时

推荐：

- 保留实时监控页面
- 导出最终报告
- 重点看异常事件明细和证据目录

---

## 10. 结论

播放器压测模块当前已经从“单纯采样工具”升级为“电视端卡顿诊断工具”，其核心价值体现在：

- 能自动识别电视端播放风险
- 能区分确认问题与风险样本
- 能给出研发可执行的排查入口
- 能沉淀事件级证据，方便复盘

当前最适合的定位是：

- 可作为日常冒烟、问题定位、版本风险初筛工具
- 在具备足够时长和业务负载的前提下，可逐步承担更强的上线评审辅助角色
