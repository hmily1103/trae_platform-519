# 第一部分：概述

## 1.1 背景与痛点

在 VOD / KTV / 机顶盒业务发版过程中，常见痛点包括：

- **全量回归成本高**：每次发版跑完整回归套件耗时长、占用设备多。
- **变更影响难判断**：只看 Git Diff，难以快速回答「最少该验什么」。
- **工具分散**：点歌、播放压测、UI 自动化、组合测试等模块各自为政，结果难汇总。
- **上线结论缺乏依据**：缺少统一的、可追溯的质量门禁与报告。

精准回归旨在解决：**从一次代码变更出发，自动收敛最小验证集，编排各执行器，汇总结果并给出质量结论**。

## 1.2 产品定位

### 是什么

变更驱动的 **精准回归编排与质量门禁** 系统：

```text
Git Diff + 需求说明
  → 变更影响分析
  → 风险模型 + 最小验证集
  → 执行器映射与追踪
  → 结果回收 + 质量门禁
  → 正式报告 / 飞书
```

### 不是什么

| 误解 | 实际情况 |
|------|----------|
| 全自动发版系统 | **人工在环**：机器收敛范围，测试负责人做最终放行 |
| 全量用例生成器 | 生成的是 **最小验证集**（通常 5～10 条），不是完整回归套件 |
| 替代所有测试工具 | **编排层**，实际执行仍由各业务模块完成 |
| 100% 代码级精准 | LLM + 规则为主；CodeGraph 静态分析为 **可选增强** |

### 核心价值

帮助测试负责人回答三个问题：

1. 这次改动 **真正影响什么**？
2. **最少要验证哪些** 高价值场景？
3. 当前结果 **是否建议上线**？

## 1.3 设计原则（红线）

| 原则 | 说明 |
|------|------|
| 人工在环 | `collect` 不自动改门禁；`sync` 只认绑定报告；采纳需人工确认保存 |
| 失败即降级 | LLM / Mastra / CodeGraph 任一失败不阻断主分析流程 |
| 证据可追溯 | 风险证据、`agent_trace`、执行证据、报告均可审计 |
| 绑定才同步 | 未带 `precision_analysis_id` 的执行报告 **不会** 自动计入门禁 |
| 观察优先 | 默认 `gate_mode=observe`；稳定后再试点 `enforce` |

## 1.4 适用场景

**适用：**

- VOD / KTV / STB 版本发版前回归范围收敛
- MR / 发布分支变更影响评估
- 多执行器测试结果统一汇总与上线决策

**不适用：**

- 要求 100% 无人值守自动放行的场景
- 无被测环境（设备、服务端）且需验证运行时行为的场景（可走非运行时轻量方案）

## 1.5 术语表

| 术语 | 说明 |
|------|------|
| 分析单 | 一次精准回归任务，ID 形如 `pt_<timestamp>_<uuid>` |
| 风险 | `risks[]`，VOD 六类之一，含 P0/P1/P2 |
| 测试点 | `test_points[]`，最小验证集条目，ID 形如 `T01` |
| 执行项 | `execution_plan[]`，测试点映射到执行器，ID 形如 `E01` |
| 质量门禁 | `quality_gate`，上线结论枚举 |
| 采纳率 | 推荐测试点中被给出明确结论（非 PENDING）的比例 |
| CodeGraph | 本地静态代码影响分析 CLI（可选） |
| tester_brief | 测试负责人解读（规则生成的人话摘要） |

# 第二部分：功能说明

## 2.1 用户角色

| 角色 | 职责 |
|------|------|
| 测试负责人 | 发起分析、确认方案、组织执行、同步/回填结果、给出上线结论 |
| 研发 | 提供 Diff 与需求说明、回应 `must_confirm` 项 |
| 平台管理员 | 配置 LLM、飞书 Webhook、CodeGraph、Mastra 等 |

## 2.2 功能全景

```text
┌──────────────┐    ┌──────────────┐    ┌──────────────┐    ┌──────────────┐
│   输入层     │ →  │   分析层     │ →  │   执行层     │ →  │   结论层     │
│ Diff/需求/Git│    │ 风险/测试点  │    │ 执行器映射   │    │ 门禁/报告    │
└──────────────┘    └──────────────┘    └──────────────┘    └──────────────┘
                           ↑
                    CodeGraph（可选）
                    Agent（ReAct/三步链）
```

## 2.3 页面与操作流程

### 2.3.1 页面入口

- URL：`/precision_test/`
- 布局：
  - **左侧**：需求说明、Git Diff、只读 Git 来源、测试环境
  - **右侧 Tab**：风险、测试点、执行结果、报告、Agent 轨迹

### 2.3.2 标准操作流程

1. 填写 **版本号**、**需求说明**、**项目类型**（默认 `vod`）
2. **粘贴 Diff**，或通过「只读 Git」从仓库拉取
3. （可选）填写 **设备 ID**、机顶盒型号、固件、服务端地址
4. 点击 **「生成精准回归方案」**
5. 阅读 **测试负责人解读** 与风险列表
6. 检查 **最小验证集** 与 **映射依据**（`routing_reason`）
7. 点击执行器链接，在各模块完成测试（URL 已预填追踪参数）
8. 返回精准回归页：
   - **采集状态**：查看各执行器最近运行快照
   - **同步绑定结果**：自动回填带绑定的 PASS/FAIL
   - 或人工修改后 **保存并计算门禁**
9. **生成正式报告** → 报告中心 / 飞书推送

### 2.3.3 Git 只读拉取

| 操作 | API |
|------|-----|
| 预览 Diff | `POST /precision_test/api/git/preview` |
| 自动识别发布基线 | `POST /precision_test/api/git/detect_baseline` |

约束：只读、不 push；支持 GitLab 等 URL 规范化与发布 tag 基线识别。

## 2.4 风险模型（VOD 六类）

| 分类 | 典型范围 | 优先级倾向 |
|------|----------|------------|
| 点歌 | 搜索、点歌、收藏、队列、切歌、歌单 | P0 |
| 播放 | 起播、暂停、卡顿、黑屏、无声、音画、解码 | P0 |
| 设备 | 固件、型号、启动、重启、升级、ADB | P1 |
| 服务端 | 接口、数据库、缓存、并发、房台 | P1 |
| 跨端 | 机顶盒 / Pad / 中控 / 移动端状态一致 | P1 |
| 异常 | 断网、弱网、超时、重试、降级（**主线为容灾时**） | P1 |

> **注意**：普通业务代码中的 `try/except`、错误返回 **不应** 归为「异常」；系统通过 `refine_category` 自动纠正 LLM 误判。

### 风险字段说明

| 字段 | 说明 |
|------|------|
| `id` | R01、R02… |
| `category` | 六类之一 |
| `title` | 风险标题 |
| `scope` | 影响范围描述 |
| `priority` | P0 / P1 / P2 |
| `impact_type` | direct（直接）/ indirect（间接） |
| `evidence` | 文件路径、符号、需求片段等 |
| `confidence` | high / medium / low |
| `affected_users` | 受影响用户/场景 |

## 2.5 测试负责人解读（tester_brief）

分析完成后，系统自动生成 **规则化** 解读（非 LLM 自由发挥）：

| 字段 | 含义 |
|------|------|
| `plain_summary` | 人话结论（如是否存在 P0、是否非运行时改动） |
| `must_confirm` | 需研发确认的设计问题 |
| `verification_focus` | 建议优先验证清单 |
| `suggested_action` | 建议下一步（如「先确认设计意图，再执行最小验证集」） |

**已内置业务规则示例：**

- 播控栏 / `PlayControlBar` 相关改动 → 播放控制、图层遮挡验证
- `getMainBoxModel` / 主盒型号 → 需研发确认是否故意固定 X9
- Pad / 扫码初始化 → 跨端连接与状态恢复

### 2.7.2 细粒度路由（映射依据）

系统 **不仅** 按风险大类选执行器，还会综合以下文本做关键词匹配：

- 测试点 `title`、`steps`、`expected`
- 风险 `title`、`scope`、`evidence`

命中 `EXECUTOR_ROUTING_RULES` 后，执行项携带 `routing_reason` 字段，便于人工判断是否更换执行器。

**路由规则摘要：**

| 命中关键词（示例） | 优先执行器 |
|-------------------|------------|
| 点歌、搜索、队列、收藏 | 点歌与搜索 |
| 接口、幂等、并发、缓存、数据库 | API 压测 |
| 播放、播控栏、卡顿、黑屏、图层 | 播放器压测 |
| 页面、按钮、弹框、布局、Pad | UI 自动化 |
| CPU、内存、FPS、卡顿 | 性能监控 |
| Crash、ANR、异常日志 | 日志监控 |
| 跨端、断网、弱网、组合 | 组合测试 |
| 启动、重启、升级、固件 | 中控重启 |
| 稳定、随机、长稳 | Monkey |
| 高负载、QPS、ARM | ARM 服务器压测 |

## 2.8 执行结果回收

### 2.8.1 三种方式

| 方式 | 操作 | 是否改门禁 | 说明 |
|------|------|------------|------|
| 采集状态 | 「采集状态」按钮 | **否** | 只看各执行器最近运行快照 |
| 同步绑定 | 「同步绑定结果」 | **是**（有绑定时） | 从执行器报告自动回填 |
| 人工回填 | 修改表格 + 「保存并计算门禁」 | **是** | 无结构化报告时使用 |

### 2.8.2 执行状态

| 状态 | 含义 |
|------|------|
| `PENDING` | 未执行 |
| `PASS` | 通过 |
| `FAIL` | 失败 |
| `BLOCKED` | 阻断 |
| `SKIPPED` | 跳过 |
| `ENV_ERROR` | 环境问题（设备离线、ADB 异常等） |

### 2.8.3 「采纳该组为通过」

当 **采集状态** 显示某执行器「最近运行通过」时，可一键将该组仍为 `PENDING` 的项预选为 `PASS`。

> **仍需点击「保存并计算门禁」才生效。**

### 2.8.4 已支持自动采集/同步的执行器

| 执行器 | 报告端点 |
|--------|----------|
| song_order | `/song_order/api/history` |
| ui_automation | `/ui_automation/api/reports` |
| monkey | `/monkey/api/reports` |
| player_stress | `/player_stress/api/reports` |
| log_monitor | `/log_monitor/api/alerts` |
| combined_test | `/combined_test/api/reports` |

以下执行器 **暂无** 结构化报告端点，需人工回填：`api_stress`、`performance_monitor`、`reboot`、`server_stress`。

## 2.9 质量门禁

### 2.9.1 门禁结论

| 结论 | 含义 |
|------|------|
| `PASS` | P0 全部通过，无阻断项 |
| `CONDITIONAL_PASS` | 存在非阻断失败，需接受遗留风险 |
| `BLOCKED` | P0 未完成/失败，或 P1 失败且无 workaround |
| `REVIEW_REQUIRED` | 环境异常，或测试尚未全部执行 |

### 2.9.2 判定逻辑（摘要）

```text
P0 存在 PENDING / BLOCKED / SKIPPED  → BLOCKED
P0 存在 FAIL                         → BLOCKED
P0 存在 ENV_ERROR                    → REVIEW_REQUIRED
P1 失败且无 workaround               → BLOCKED
P1/P2 失败（有可规避方案）            → CONDITIONAL_PASS
任意 ENV_ERROR                       → REVIEW_REQUIRED
存在 PENDING                         → REVIEW_REQUIRED
否则                                 → PASS
```

### 2.9.3 门禁模式

| 模式 | 行为 |
|------|------|
| `observe`（默认） | 只给建议，`release_blocked = false` |
| `enforce` | 当结论为 BLOCKED 时，`release_blocked = true` |

### 2.9.4 指标

| 指标 | 说明 |
|------|------|
| `coverage_rate` | 已给出结论的执行项 / 总执行项 |
| `adoption_rate` | 已采纳测试点 / 推荐测试点 |
| `llm_adoption_rate` | AI 生成测试点的采纳率 |
| `template_adoption_rate` | 模板补充测试点的采纳率 |

## 2.10 报告与通知

| 类型 | 说明 |
|------|------|
| 影响报告 `impact_report` | 分析完成时生成的 Markdown 摘要 |
| 正式报告 `report_markdown` | 调用 finalize 后生成，含执行明细 |
| 统一报告中心 | `/unified/report/<analysis_id>` |
| 飞书 | 配置 Webhook 后一键推送质量结论卡片 |

**飞书配置：**

- 环境变量：`PRECISION_TEST_FEISHU_WEBHOOK`
- 或 `config/llm_config.json` 中 `precision_test_feishu_webhook` / `feishu_webhook`

## 2.11 非运行时变更

系统自动识别以下 **低风险** 变更，**不推荐完整 VOD 主链路回归**：

| change_type | 示例 |
|-------------|------|
| `ai_tooling` | `.claude/`、`.codex/`、协作配置 |
| `documentation` | Markdown、README、docs |
| `test_only` | 仅测试代码或测试数据 |

处理方式：

- 风险降为 **P2**
- 生成 **3 条** 轻量验证点（配置校验、文档准确性、确认不进产物等）

### 3.3.1 主分析接口 `POST /api/analyze`

**请求体示例：**

```json
{
  "code_diff": "--- a/app/player.py\n+++ b/app/player.py\n...",
```

**响应要点：**

- `analysis_id`
- `analysis`：完整分析单 JSON
- `impact_report`：Markdown 摘要
- `diff_summary`：规则层变更摘要

**限制：**

- `code_diff` 最大 100,000 字符
- `requirement` 最大 30,000 字符
- `project_type` 仅支持：`vod`、`backend`、`frontend`、`mobile`、`fullstack`

## 3.4 分析主流程

```text
1. 校验输入
2. _extract_diff_summary(code_diff)
   ├── 文件列表、增删行
   ├── risk_signals（关键词规则）
   └── change_type / runtime_impact
3. codegraph_impact = analyze_diff_impact()  [可选，失败静默]
4. agent_result = run_risk_agent(..., codegraph_impact)
5. model = normalize_analysis(agent_result, ...)
6. 附加 agent_trace、metrics、impact_report
7. store.save(model)
8. 返回结果
```

## 3.6 Agent 技术实现

### 3.6.1 降级链

```text
ReAct（call_llm_with_tools，最多 6 轮）
  ├── 工具：search_code_symbol、search_code_impact
  └── Critic 修订（P0/P1 缺证据、低置信过多）
        ↓ 失败或 LLM 不支持 function calling
Mastra HTTP（环境变量 MASTRA_ANALYSIS_URL）
        ↓ 失败或未配置
本地三步链
  ├── Step1 Candidate：粗分候选风险区域
  ├── Step2 Classify：分类、优先级、测试点
  └── Step3 Validate：去重、CodeGraph 覆盖核对
        ↓ 失败
engine._default_risks（规则模板兜底）
```

### 3.6.2 analysis_source 枚举

| 值 | 含义 |
|----|------|
| `agent_react` | ReAct 工具调用链路成功 |
| `agent_mastra` | Mastra 委托成功 |
| `agent` | 本地三步链 |
| 规则兜底 | Agent 全部失败时的默认风险 |

### 3.6.3 agent_trace 结构

每步记录：

- `step`：轮次
- `type`：`think` / `tool` / `final`
- `content` / `observation`：思考与工具观察摘要
- `duration_ms`：耗时（三步链）

### 3.6.4 分类纠正 refine_category

当 LLM 将普通业务改动标为「异常」时，确定性规则会：

1. 若文本命中点歌/播放/设备等功能信号 → 归回对应业务类
2. 仅当改动主线确实是容灾/韧性 → 保留「异常」

## 3.7 Engine 核心算法

### 3.7.1 _build_test_points

```text
1. 保留 LLM 有效测试点（risk_ids 合法 → source=llm）
2. 不足目标数 → _test_templates 按风险分类补充（source=template）
3. 仍不足 → fallback_scenarios 通用场景补齐
4. 按 P0/P1/P2 排序，编号 T01..T20
```

### 3.7.2 _executor_for_point

```text
1. 拼接文本 = title + steps + expected + risk 信息 + evidence
2. 遍历 EXECUTOR_ROUTING_RULES（正则 + categories 过滤）
3. 命中第一条 → executor + mode + routing_reason
4. 未命中 → CATEGORY_EXECUTORS 默认映射
```

### 3.7.3 calculate_quality_gate

见 [2.9.2 判定逻辑](#292-判定逻辑摘要)。

返回字段包括：`decision`、`mode`、`enforced`、`release_blocked`、`reasons`、`coverage_rate`、`p0_total`、`p0_passed`。

## 3.8 CodeGraph 集成

### 3.8.1 是什么

本地 CLI 工具，基于 tree-sitter 建代码知识图谱，支持：

- `codegraph init` — 建索引
- `codegraph impact <symbol> -j` — 查符号影响链
- `codegraph affected` — 查受影响测试（辅助，非主路径）

### 3.8.2 配置

`modules/precision_test/codegraph_config.json`：

```json
{
  "enabled": false,
  "repo_path": "",
  "test_glob": "**/test_*.py"
}
```

或环境变量 `CODEGRAPH_REPO_PATH`（设置后自动 `enabled=true`）。

### 3.8.3 启用后作用

| 作用 | 说明 |
|------|------|
| 硬证据 | `changed_files`、`impact_symbols`、`affected_tests` 注入 Agent prompt |
| ReAct 工具 | `search_code_impact` 供 Agent 主动查询 |
| Validate 步 | 核对 CodeGraph 受影响测试是否在方案中有覆盖 |
| 前端展示 | 分析结果页显示影响透视摘要 |

### 3.8.4 限制

- 静态分析，看不到反射、动态分发、AOP
- 需本机安装 `codegraph` CLI
- `repo_path` 应指向 **被测业务仓库**（非 trae_platform 本身，除非分析平台代码）
- 失败时 `available=false`，**不阻断**主流程

### 3.8.5 启用检查清单

1. 安装 CodeGraph CLI（`npm i -g codegraph` 或项目内 binary）
2. 编辑 `codegraph_config.json`，设置 `enabled: true` 与 `repo_path`
3. 首次分析会自动 `codegraph init`（可能较慢）
4. 用真实 Diff 生成方案，确认 `codegraph_impact.available === true`
5. 检查 `affected_tests` 是否合理

## 附录 D：常见问题 FAQ

**Q：为什么「采集状态」不自动改门禁？**  
A：执行器「最近运行」无法可靠关联到本次分析的特定测试点，强行自动回填会误把其他任务结果算进来。

**Q：为什么「同步绑定结果」更新了 0 项？**  
A：常见原因：执行时未从精准回归链接进入（缺少 `precision_*` 参数）；执行器报告未写绑定字段；该执行器无报告端点。

**Q：非运行时改动为什么只有 3 个测试点？**  
A：文档/AI 配置/纯测试改动不进入产品运行时，系统降档为 P2 轻量验证，不推荐全链路回归。

**Q：observe 和 enforce 有什么区别？**  
A：observe 只展示建议结论；enforce 在 BLOCKED 时标记 `release_blocked=true`，可用于试点阻断发布流程。

**Q：CodeGraph 必须开吗？**  
A：不必。默认关闭，主流程靠 LLM + 规则；开启后增加代码级影响证据。

**Q：能完全自动化吗？**  
A：不能，也不设计为完全自动化。分析和方案生成可自动化，执行与放行决策保留人工在环。
