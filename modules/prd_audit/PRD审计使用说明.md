## PRD 审计使用说明

> 面向对象：0 基础的产品 / 测试 / 研发 / 项目经理  
> 目标：看完后，你能自己跑一遍 PRD 审计、看懂结果，并知道规则库 / 测试知识库 / 学习 MVP 分别干什么。

---

## 1. 我能用它做什么？

PRD 审计帮你做四件事：

1. **检查 PRD 是否写完整**：  
   - 是否有功能列表？  
   - 是否说明了角色、流程、状态、异常？  
   - 是否讲清楚数据与权限？

2. **自动找需求漏洞**（Stage2 漏洞扫描）：  
   - 规则库（静态规则）找结构性问题  
   - 大模型（DeepSeek / 火山等）找语义和隐藏风险

3. **输出易读的审计报告**（L1/L2/L3）：  
   - L1 管理摘要：给老板 / PM  
   - L2 产品分析：给产品 / 业务  
   - L3 技术审计：给研发 / 测试

4. **沉淀可复用的知识**：  
   - 保存每次审计的“快照”，用于后续规则学习（学习 MVP）  
   - 可以配合「测试知识库」积累功能图谱与历史 Bug 模式

## 2. 如何启动 & 打开 PRD 审计？

### 2.1 启动服务

在项目根目录（例如 `D:\trae-code\trae_platform`）执行：

```bash
python app.py
```

成功标志：

- 终端里出现类似：
  - `PRD Audit (standalone) module loaded successfully`
  - `访问地址: http://127.0.0.1:5000`

### 2.2 打开 PRD 审计页面

在浏览器访问：

- `http://127.0.0.1:5000/prd_audit/`

页面布局：

- 左侧：**输入 PRD**  
- 右侧：**审计报告 + 附加信息**  
- 右上角：  
  - `LLM 配置` 按钮（全平台大模型配置入口）  
  - 未来可能有「学习MVP」按钮

## 3. 第一次使用：从 0 到拿到一份审计报告

### 3.1 准备 PRD 文本

支持三种方式：

1. **粘贴飞书文档链接**  
   - 直接粘贴 URL 到左侧输入框  
   - 系统会尝试从飞书拉取内容，失败会提示

2. **直接粘贴 PRD 文本**  
   - 从飞书 / Word 中复制全文  
   - 粘贴到输入框即可  
   - 这是最稳妥的方式

3. **上传 PDF / Word**  
   - 点击「上传 PDF/Word」  
   - 选择 `.pdf` 或 `.docx` 文件  
   - 系统会自动解析文本并填入输入框

如果解析失败，错误会弹窗提示，你可以改用「复制 + 粘贴」的方式。

### 3.2 配置 / 确认大模型（全平台通用）

右上角点击 **「LLM 配置」** 打开配置弹窗。

> 注意：这里改的是**全平台共用**的大模型设置（文件 `modules/test_case/llm_config.json`）。

在弹窗中你会看到：

- **提供方**（下拉框）：
  - `DeepSeek`
  - `火山引擎（Ark / 豆包）`
  - `Google Gemini`（如已接入）
- **Base URL**：
  - DeepSeek：`https://api.deepseek.com/v1`
  - 火山 Ark：`https://ark.cn-beijing.volces.com/api/v3`
- **Model**：
  - DeepSeek：通常填 `deepseek-chat`
  - 火山：填你在火山控制台看到的模型 ID，例如：`doubao-seed-1-6-251015`
- **API Key**：
  - 粘贴对应平台提供的 key 字符串

保存后：

- 会写入 `modules/test_case/llm_config.json`
- PRD 审计 / 用例管理等所有使用 `utils.llm_client.call_llm` 的模块都会用这份配置

### 3.3 选择是否启用大模型

在左侧「输入 PRD」卡片顶部，有一个勾选框：

- `使用大模型`（默认勾选）

含义：

- **勾选**：
  - Stage2 会同时使用：
    - 本地规则库（`prd_scan_rules_v2.json`）
    - 大模型（取决于你在 LLM 配置里选了谁）
  - 两者结果合并去重，报告更全面
- **不勾选**：
  - Stage2 只用本地规则库，不调用大模型
  - 适合：
    - 没配大模型但想先用规则库打基线
    - 做「规则库效果回归」时

### 3.4 点击「开始分析」

准备就绪后：

1. 确保输入框有内容（系统会校验空内容）
2. 根据需要勾选 / 取消「使用大模型」
3. 点击左下角「开始分析」

此时：

- 状态标签会显示「分析中…」
- 右侧「审计报告」区域会实时显示流水线进度：
  - `Stage1：PRD结构解析中…`
  - `Stage2：PRD漏洞扫描中…`
  - `Stage3：... 报告生成中…`

完成后：

- 右侧会出现一份 Markdown 报告文本
- 顶部会显示：
  - `复制`
  - `当前 .md`
  - `当前 .docx`
  - 「按层级下载」的下拉菜单
  - 「保存为测试用例」按钮

## 4. 如何阅读审计报告（L1/L2/L3）

### 4.1 报告层级介绍

右侧报告区域，顶部有 3 个按钮：

- `管理摘要 (L1)`  
  - 给老板 / 项目经理看，用于「要不要立项 / 上线」
  - 强调结论、风险等级、下一步建议

- `产品分析 (L2)`  
  - 给产品 / 业务侧看，2–3 页内容
  - 强调功能覆盖、业务流程、边界与异常

- `技术审计 (L3)`  
  - 给研发 / 测试看，细节最丰富
  - 包含更多技术性视角和缺陷列表

你可以随时切换层级：

- 哪个按钮高亮，就表示当前显示的是哪一层级
- 提示文字会显示「当前展示：xxx」

### 4.2 标题中的「本地规则体检版」说明了什么？

如果报告标题中出现：

> `（本地规则体检版，无大模型推理）`

说明：

- 本次调用没有成功使用大模型，原因可能是：
  - `LLM 配置` 里没有正确配置 key / model
  - 大模型调用报错（网络 / 超时 / provider 报错）
- 流水线检测到 Stage2 中存在一条「扫描引擎 / 扫描异常」的缺陷，于是判定 `offline_mode = True`

对你来说：

- 这份报告仍然有价值（基于规则库的体检）
- 若你期望使用大模型，需要：
  - 打开「LLM 配置」，检查 provider / model / key 是否有效
  - 或把报错日志给平台同学排查

## 5. 规则库（Rule Library）：怎么添加 / 调整规则？

### 5.1 规则库文件位置

主要规则库文件：

- 正式库：`modules/prd_audit/prd_scan_rules_v2.json`
- 旧版：`modules/prd_audit/prd_scan_rules.json`（可以理解为 v1，通常不改）

另外，学习相关文件（后面会提到）：

- 草案：`modules/prd_audit/learning_repo/prd_scan_rules_v2.draft.json`
- 已应用：`modules/prd_audit/learning_repo/prd_scan_rules_v2.applied.json`
- 备份：`modules/prd_audit/learning_repo/prd_scan_rules_v2.backup.*.json`

### 5.2 一条规则的结构（示例）

在 `prd_scan_rules_v2.json` 中，每条规则大致长这样：

```json
{
  "rule_id": "STATE_001",
  "category": "STATE_MACHINE",
  "rule_name": "系统未定义全局状态",
  "severity": "P0",
  "weight": 10,
  "description": "系统存在多个功能模块，但未定义统一状态集合（states 为空或均为【PRD未说明】）。",
  "detector": "state.missing_global_states",
  "detection_logic": "Stage1.states 为空或均为【PRD未说明】",
  "llm_check_prompt": "分析该 PRD 是否定义系统状态集合...",
  "risk_reason": "没有全局状态集合，模块切换与恢复规则无法统一，开发容易产生逻辑冲突与不可预期行为。",
  "suggestion": "补充系统状态机定义（状态集合+进入/退出条件+恢复规则）。",
  "example_fix": "定义状态 Idle→广告→投屏→游戏，并说明打断与恢复。",
  "enabled": true
}
```

对非技术同学，最重要的是：

- `rule_name` + `description`：规则在找什么问题
- `severity`：严重程度（P0/P1/P2）
- `risk_reason` / `suggestion` / `example_fix`：可以直接用到评审/整改文档中
- `enabled`：是否启用该规则

### 5.3 如何「关闭一条过于吵的规则」？

如果你发现某条规则**总在误报 / 过于敏感**：

1. 用编辑器打开：`modules/prd_audit/prd_scan_rules_v2.json`
2. 搜索对应的 `rule_id` 或 `rule_name`
3. 把这一条规则的：

   ```json
   "enabled": true
   ```

   修改为：

   ```json
   "enabled": false
   ```

4. 保存文件即可（规则文件本身读取时不一定需要重启服务，但如果不确定，重启一次是最保险的做法）

之后再跑 PRD 审计，这条规则就不会再产生新缺陷。

### 5.4 如何「手动添加一条规则」？

不推荐 0 基础同学直接大量手写规则，但你完全可以：

1. 找一个现有规则作为模板
2. 在 `rules` 数组的末尾追加一条类似结构的 JSON 对象
3. 按照实际需求修改：
   - `rule_id`：比如 `FLOW_999`
   - `rule_name`：简明扼要
   - `category`：归到对应类别（STATE/FLOW/EXCEPTION 等）
   - `severity`：P0/P1/P2
   - `description` / `detection_logic` / `llm_check_prompt` / `risk_reason` / `suggestion` / `example_fix`

示例（简化版）：

```json
{
  "rule_id": "FLOW_999",
  "category": "FLOW",
  "rule_name": "未说明支付失败后的处理流程",
  "severity": "P1",
  "weight": 7,
  "description": "PRD 中提到了支付，但未说明支付失败/超时时的处理策略。",
  "detector": "",
  "detection_logic": "business_rules 或 flows 中提到“支付”，但没有出现“失败/超时/异常/降级”等字样。",
  "llm_check_prompt": "检查 PRD 中涉及支付/扣款的需求，判断是否明确说明支付失败或超时时的处理逻辑。",
  "risk_reason": "没有支付失败策略容易导致资金风险与用户投诉。",
  "suggestion": "补充支付失败/超时等异常场景的处理流程，并明确对账与重试策略。",
  "example_fix": "说明“支付失败时回滚订单状态为【待支付】，记录失败原因并提示用户。”",
  "enabled": true
}
```

保存后，下次 PRD 审计就会考虑这条规则。

## 6. 测试知识库：如何添加功能 & Bug 模式？

测试知识库是一个**人工维护的经验库**，不直接参与规则扫描，但会被其他功能利用。

### 6.1 入口位置

- 菜单：左侧侧栏的「测试知识库」
- 模板：`modules/test_case/templates/knowledge_center.html`

打开页面，你会看到：

- 上方：可展开的「填写格式说明」
- 下方：一个卡片，内有两个 Tab：
  - 功能知识图谱
  - 历史 Bug 模式

### 6.2 功能知识图谱：添加功能经验

用途：为每个功能记录「常见风险 & 对应测试策略」，方便以后复用。

**操作步骤：**

1. 进入「测试知识库」页面
2. 默认 Tab 是「功能知识图谱」
3. 点击「新增一行」
4. 填写各列：

   - 功能名称  
     - 如：`投屏`、`广告插播`、`登录注册`
   - 关键词（一行一个）  
     - 用于从 PRD 中匹配到这个功能  
     - 如：  
       - `投屏`  
       - `cast`  
       - `screen mirror`
   - 风险（一行一个）  
     - 如：  
       - `连接失败`  
       - `中断后无法恢复`  
       - `音画不同步`
   - 测试策略（一行一个）  
     - 如：  
       - `弱网测试`  
       - `多设备兼容`  
       - `状态机测试`
   - 测试点示例（一行一个）  
     - 如：  
       - `弱网下发起投屏，观察连接成功率`  
       - `投屏中断后恢复播放是否回到正确位置`

5. 可以为多个功能各新增一行
6. 填完后点击右上角「保存全部」

### 6.3 历史 Bug 模式：记录典型问题

用途：  
把「已经发生过的严重 Bug」整理成模式，以后评审 / 设计测试时能提前想到。

**操作步骤：**

1. 同一页面，切换 Tab：`历史 Bug 模式`
2. 点击「新增一行」
3. 填写：

   - 关联功能  
     - 如：`投屏`、`支付`、`登录`
   - Bug 标题  
     - 如：`投屏后声音不同步`
   - 风险/现象说明  
     - 如：`音画不同步，严重影响观看体验`
   - 建议测试/防护策略  
     - 如：`在多机型、多网络场景下增加音画同步测试`

4. 重复上述步骤，录入多个经典 Bug 模式
5. 点击右上角「保存全部」

## 7. 学习 MVP：让规则库自己长大

学习 MVP 负责「把历史审计结果变成候选规则」。

### 7.1 背后有什么文件？

目录：`modules/prd_audit/learning_repo/`，重要文件：

- `snapshots/` 目录：  
  - 每次 PRD 审计的一份快照（包括缺陷列表、P0/P1/P2 数、offline_mode 等）
- `index.json`：  
  - 所有快照的索引（类似总目录）
- `rule_candidates.json`：  
  - 从快照里自动生成的「候选规则」列表
- `prd_scan_rules_v2.draft.json`：  
  - 候选规则的“草案规则库”
- `prd_scan_rules_v2.applied.json`：  
  - 已经人工筛选 + 应用的规则集合
- `prd_scan_rules_v2.backup.*.json`：  
  - 每次发布前，对正式库的备份
- 正式库：`modules/prd_audit/prd_scan_rules_v2.json`

### 7.2 它是怎么工作的？（概要）

1. 你每跑一次 PRD 审计，流水线会调用 `audit_learning.save_audit_snapshot`：
   - 把这次的缺陷结果等信息存成一个 snapshot
2. 当你跑了很多次审计后，可以在 UI 上点击「学习MVP」：
   - 选择若干快照 → 点「生成草案」
3. 系统会：
   - 把高频、高风险的缺陷模式提炼成「候选规则」
   - 写入 `rule_candidates.json` 和 `prd_scan_rules_v2.draft.json`
4. 你在 UI 勾选你认可的规则 → 点「应用勾选规则」：
   - 勾选的规则会存入 `prd_scan_rules_v2.applied.json`
5. 最后点「发布为正式规则」：
   - 把当前 `prd_scan_rules_v2.json` 备份成 backup
   - 再把 applied 中的规则合并进正式规则库

### 7.3 建议的使用节奏（给你一个简单操作 SOP）

- **日常**：
  - 像平时一样用 PRD 审计，不用管学习仓库，它会自动存快照
- **每周一次**：
  1. 打开学习MVP页面
  2. 选择「最近一周」的快照
  3. 点击「生成草案」
  4. 在候选规则列表中：
     - 优先勾选：
       - 命中次数多
       - 严重级别为 P0/P1
  5. 点击「应用勾选规则」
  6. 确认无误后，点击「发布为正式规则」
- **出现问题时**（比如新规则过于吵 / 误报多）：
  - 在学习MVP里选一个稳定时期的备份版本（backup 文件）
  - 点击「回滚」，恢复到旧的规则库

## 8. 推荐的团队使用方式（综合 3 大块）

### 每个新需求 / 新项目

1. 在评审前，让需求方提供尽量完整的 PRD
2. 测试或架构同学：
   - 在 PRD 审计里跑一遍
   - 把报告（尤其 L1/L3）纳入评审材料
   - 如有「P0 问题」，在评审会上重点讨论

### 每周一次（规则 + 知识维护）

1. 用学习MVP：
   - 查看最近一周的审计结果
   - 选几条「值得长期关注」的问题固化成规则
2. 用测试知识库：
   - 为新功能补上功能图谱记录
   - 把这一周遇到的典型 Bug 加到「历史 Bug 模式」

### 每月 / 每季度一次（回顾）

1. 查看规则库备份变化（看规则是否越来越丰富）
2. 查看学习MVP指标（如：`local_only / llm_only / hybrid`）
3. 根据团队反馈，对最吵的规则做一次清理（关闭或调整）

## 9. 常见问题（FAQ）

### Q1：我改了 LLM 配置，要重启服务吗？

- 不需要。  
- `llm_config.json` 每次调用前都会重新读取，保存后新请求立即生效。  
- 只有改了 Python 代码或模板文件时，才需要重启 `python app.py`。

### Q2：报告里写「本地规则体检版，无大模型推理」，怎么办？

- 说明本次没有正确使用大模型。  
- 请检查：
  1. 点开「LLM 配置」：
     - 提供方是否正确（DeepSeek / 火山）
     - Base URL 是否正确
     - Model 是否你在控制台开通的模型
     - API Key 是否填写且有效
  2. 若仍不行，把报错日志 / 提示交给平台同学排查。

### Q3：学习MVP会不会“弄坏”现有规则库？

- 每次「发布为正式规则」前，系统都会自动备份旧规则到 `learning_repo/prd_scan_rules_v2.backup.*.json`。  
- 如果新规则质量不好，可以通过「回滚」恢复到之前的版本。  
- 建议：
  - 每次发布少量规则，分批次迭代，而不是一次性全量发布。
